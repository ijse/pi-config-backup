# 独立测试工作流

## 目标与适用范围

让生产实现与测试设计/编写由不同 Agent 承担，减少自证偏差，尽早推进测试。另一个 Agent 只读代码或只运行主代理写的测试，不等于完成这项分工。

- 主代理读取本 Skill 后负责调度；如果你本身是子代理，只完成交付任务，不嵌套启动子代理。
- 新增功能、行为变更、Bug 修复默认适用。纯文档、纯格式等明确不影响行为的任务可豁免，最终简述理由。
- 不能因代码少、时间紧或“显然正确”豁免。配置、依赖及重构若影响运行行为，同样适用。
- 若已有测试充分覆盖目标，测试子代理可解释为何不需新增测试，但必须独立检查方案并实际验证；不为数量制造重复测试。
- 这是提示词层面的流程，不是权限沙箱，也不保证消除模型的共同盲点。不安装插件，不自动 commit、push 或部署。

## 职责和边界

**主代理**：澄清需求、确定契约、编写/修复生产代码、处理需求歧义、协调文件所有权、复核实际 diff 与测试结果。

**测试子代理**：依据需求独立设计用例，编写/维护测试及获准的 fixtures，执行验证，报告缺陷、证据、覆盖缺口。可阅读源码理解接入点，但不得把实现输出直接当作预期结果。

- 生产文件归主代理；明确列出的测试文件归测试子代理。测试配置、锁文件和共享 fixtures 必须指定唯一所有者，不可同时修改。
- 测试子代理默认不得改生产代码。主代理不得为变绿而删除测试、降低断言或加 skip/xfail；测试本身有错时，先核对需求证据，再交测试子代理修正。
- 需求和测试契约可经确认修订，不是永远冻结；修订需说明依据并重新验证，不能跟着错误实现走。
- 不修改或清理用户既有未提交工作，不读取/输出无关密钥，不接触生产数据，不调用真实付费或有副作用的服务。
- 需要新依赖时遵循项目与全局安装规则；不要自行全局安装，不为该流程强加新测试框架。

## 1. 编码前建立测试交付契约

读取项目适用的 AGENTS.md、测试入口与现有用例。若项目使用 Git，记录 `git status --short` 和当前基线；非 Git 项目记录改动文件范围。不要覆盖已有修改。

明确以下内容，并只把相关事实交给子代理，不复制整个主会话或实现者的推理：

1. 需求、可观察行为、验收标准、兼容性要求和不做什么。
2. 公开接口/输入输出，以及哪些问题尚未确认。
3. 项目绝对路径、可读范围、可写测试路径、禁止改动的文件及共享资源所有者。
4. 已核实的测试框架、命令、环境、可用 fixtures；未知项明确标注“待查证”。
5. 成功标准、可用测试预算、外部服务限制和报告格式。

**尽早启动测试设计，不要等生产实现全部完成。** 通常一个测试子代理即可，无需把设计、编写、执行再拆成三个人。

## 2. 选择最小充分的执行方式

### 先测试，后实现（默认）

适用于 Bug、业务规则和边界条件清晰的变更。

1. 测试子代理设计用例、编写最小测试、执行 RED 验证，然后交回结果。
2. 主代理确认失败确实反映缺陷/缺失行为，再实现生产代码。
3. 启动新的测试验证 job，提供先前的用例、文件与证据，检查 GREEN 和相关回归。

编译失败、缺依赖、网络失败等不得冒充行为级 RED。新接口尚不存在时可以报告接入失败，但必须说明局限，接口接通后继续验证目标行为。若原版已通过，先检查用例是否真正覆盖需求。

### 契约稳定后并行

测试子代理先发送或返回测试方案；主代理确认接口后，双方只写自己拥有的文件。

- 开发期间可并行编写测试，但不将正在变化的工作树上的运行结果作为最终结论。
- 最终测试必须在相关文件停止写入后运行；主代理等待验证结束才继续修改。
- 同一数据库、端口、快照、构建目录等共享资源也可能冲突，不能只检查源文件是否重叠。
- 契约未稳定、文件无法分开或资源冲突时改为串行。只有项目允许且确有需要才另行建立隔离工作区；本插件不自动提供 worktree。

### 已经写完实现的任务

仍需委派独立测试设计与补充，而不是仅让子代理复述现有测试。可在安全隔离副本中针对原版验证新测试能抓住缺陷；不得对用户工作树执行破坏性回退。不能取得 RED 证据时如实记录。

## 3. 调用当前 Pi 子代理工具

以实际加载的工具 schema 为准。本 Skill 的参考接口是 `@narumitw/pi-subagents` v3：

- `subagent_spawn` 仅接受 `task`、`tools`、`thinkingLevel`、`timeout`；不要传 `agent`、`skill`、`model`、`cwd` 或 `session`。
- 角色写在 `task` 中；子代理继承主代理的模型和工作目录，可独立调整 thinkingLevel，但本接口不支持单 job 换模型。
- 子代理禁用自动 Skills 加载，不假设继承主会话历史。把本次所需规则直接写进 task，而不是只说“遵循 independent-testing”。
- 不把 AGENTS.md 中的主代理调度职责转交给子代理，不让其嵌套委派。

### 最小权限

| 任务 | tools |
| --- | --- |
| 仅方案/只读审查 | `read, grep, find, ls` |
| 写测试，不执行 | 上述工具加 `edit, write` |
| 只执行验证 | 只读工具加 `bash` |
| 写测试并验证 | 只读工具加 `edit, write, bash` |

`bash` 也能改文件；工具白名单不限制具体路径、命令或网络。路径所有权是协作约束，不是安全隔离。子代理不能调用父会话独有的浏览器/MCP 扩展工具；需要浏览器验证时，优先使用项目已有、获准的 CLI 测试工具，无法执行则报告缺口。

### 调用示例（发送前替换占位符并补齐任务）

```json
{
  "task": "你是独立测试工程师，不是主调度者，不要再委派。项目：<绝对路径>。需求与验收：<明确行为>。接口：<契约>。只允许修改：<具体测试路径>，不得修改生产文件和用户既有改动。先根据需求设计正常、边界、异常及回归用例，再编写最小充分测试；不要根据当前实现反推预期。测试入口：<已核实命令或待查证>。外部资源约束：<说明>。本轮阶段：<RED 或最终验证>。不得削弱断言或跳过测试来掩盖缺陷，不自动提交、不全局安装依赖。遇到需求歧义或范围外改动需向主代理提问。报告用例与需求映射、改动文件、工作目录、实际命令和退出码、关键输出、未验证项以及 PASS/FAIL/BLOCKED；未运行不等于通过。",
  "tools": ["read", "grep", "find", "ls", "edit", "write", "bash"],
  "thinkingLevel": "high",
  "timeout": 900
}
```

示例的 900 秒仅是可调整预算，不要求所有任务固定等待 15 分钟。

### 协调和生命周期

- 启动后保留真实 `jobId`；有独立工作就继续做，需要结果时使用 `subagent_wait({ jobId, timeout })`。
- 主代理向运行中的子代理发消息：`subagent_send({ recipient: jobId, message })`。收到子代理请求时，用 `subagent_send({ requestId, message })` 回复；二者不要同时传。
- 如需子代理提问，task 中说明：子代理使用其自身的 `subagent_send({ message })`，必要时以返回的 `requestId` 调用子代理版 `subagent_wait` 等待回复；不要在子代理里使用主代理的 jobId 等待接口。
- 等待超时不等于 job 结束；需要终止时显式 `subagent_cancel({ jobId })`。在接管相同文件前必须确认旧 job 不再写入。
- 主代理等待可能因消息到达返回 `interrupted: true`、`reason: "subagent_message"`。先处理消息；job 尚未终态且仍需结果时继续等待。子代理等待也可能被新请求打断或超时；原请求未失效时，可处理新消息后继续等待同一 `requestId`。一次 wait 返回不代表任务完成。
- 终态 job 不能续聊。需要修复后复测或继续写测试时，启动新 job，明确提供先前产物和未完成事项。
- job 的 `completed` 只代表子任务结束，不代表测试 PASS；必须读取结果。其他终态也不能推断为验证通过。
- 不在活动 job 期间 reload/重启会话；本插件的任务不跨 reload 或会话存活。

## 4. 测试质量和失败处理

测试子代理按风险选择最小充分组合，而非每次穷举所有类型：

- 正常行为、空值/缺省值、边界、非法输入和异常恢复。
- 权限/租户隔离、重复请求、顺序/并发等与当前需求相关的风险。
- 既有兼容性与历史 Bug 的回归用例。
- 使用确定性的时间、随机数和 fixtures；不依赖测试顺序，不污染真实状态。
- mock 外部边界而非 mock 掉被测业务；优先观察公共行为，避免只断言内部调用或直接复制输出作为快照。

失败须区分产品缺陷、测试错误、环境阻塞和既有失败。向主代理提供复现证据；测试错误由测试子代理修正，产品错误由主代理修复，需求歧义须澄清后继续。

默认最多进行 3 轮修复/复测；同一阻塞反复发生应提前报告，不无限重试。超出预算不代表放弃测试或可宣称完成，需向用户说明剩余问题并确认下一步。

## 5. 最终验收和报告

在双方停止修改后，测试子代理对最终文件状态执行目标测试与相关回归；无法全量运行就明确覆盖范围。验证后又有相关修改，原结果失效，需重跑受影响检查。

主代理必须亲自查看实际变更和关键断言，并在稳定文件状态下运行至少一项与风险匹配的确定性验证，不只信任子代理文字结论。不能运行时明确记录，不能称为已完整验证。用户的所有既有修改应保持完整，不自动 stage/commit。

测试子代理的交付格式：

```text
阶段：方案 / RED / 最终验证
需求覆盖：验收项 -> 测试路径/用例；未覆盖项及理由
变更：本轮修改文件；是否触及边界
验证对象：工作目录、Git HEAD（如适用）与未提交改动范围
执行证据：实际命令、退出码、关键输出/报告路径
结果：通过/失败/跳过数量（以工具实际输出为准）；没有统计则注明
风险与阻塞：未运行项、环境问题、既有失败、假设
阶段结论：PASS / FAIL / BLOCKED
```

RED 阶段的 PASS 仅表示“已观察到预期行为失败”，不是功能通过；主代理最终总结必须将二者区分。同样，方案审查通过不代表执行通过。

## 工具不可用或环境受阻

- 报告具体原因：工具缺失、启动失败、超时、权限、依赖、服务或框架缺失。
- 不自动安装替代插件、不静默退回主代理写测试、不把主代理自测标为独立验证。需要主代理接管测试编写时先征得用户同意。
- 可以继续不依赖该阻塞的安全工作，但保留验收缺口；不得宣称独立测试完成或测试通过。
- 若用户明确豁免或批准降级，记录范围与剩余风险；不能伪造子代理参与和未执行的结果。
